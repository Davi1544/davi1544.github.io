# Week 10 - Other Means to a Solution

## Overview
During Week 10, I experimented across different stages of a processing pipeline suggested by my advisor. We'll discuss the pipeline in more detail in the coming sections.

## Suggested Pipeline

In a meeting with my advisor, she suggested an entirely different pipeline to separate the undertext.

After our usual preprocessing (discussed in Week 9), we start by saving each channel in the multispectral cube as its own image. Our goal is to check if there is some channel where the undertext is separated from the overtext. But due to the nature of the multispectral cube, where each channel corresponds to an image of some specified wavelength of light reflected on the manuscript, what we'll find on each image is almost entirely dependent on the chemical composition of the ink.

Then, we transform the multispectral cube into an RGB image and begin processing this image. The argument for this step is that because certain common pigments can only reflect some small interval of wavelengths, then most of the other bands do not contain much useful information, adding to the processing time while not contributing much to the processing and separation. We'll discuss this argument in more detail later.

From there, the RGB image is turned into a LAB image. She suggested LAB instead of RGB because LAB representation tends to be more intuitive for manipulating colors and measuring distances between colors.
Using LAB, we can also use the CIEDE2000 function to calculate distances between colors.

Lastly, we apply HDBSCAN to cluster pixels together based on their color while using the CIEDE2000 function instead of the usual Euclidian distance.

The ultimate goal is that the overtext and undertext will sit in different clusters.

## Experiments

In this post, our experiments will follow the suggested pipeline, as we explore some possible directions from it.

As usual, we'll perform our experiments on the following image patch of one of the images in our dataset:

![cropped RGB conversion](/assets/img/posts/week7/colorido_cropped.png)

The first experiment I tried was simply applying HDBSCAN to the multispectral cube. The problem was the experiment took too long, despite the fact I was working with a small patch of a full image. To solve this, I decided to apply a segmentation function called SLIC to the MSI cube, which maps the hundreds of thousands of multispectral pixels into a calculated set of superpixels of specified size. For this experiment, I chose to use 10000 superpixels, which is a very large amount of an image like ours, with dimensions around 600x600.

After segmentation, I applied HDBSCAN to the superpixels and then mapped the clusters back to the original pixels, resulting in the following image:

![dry MSI cube](/assets/img/posts/week10/hdbscan_epsilon_1.0_min_samples_1.png)

As we can see, HDBSCAN did manage to cluster the text into two separate components, but those components do not clearly represent the undertext or the overtext. Furthermore, some of the text was completely lost, which inhibits reading it.

But before calculating the RGB image, I chose to apply PCA to the multispectral cube (reducing the number of channels to 3) and repeat the last experiment. The reason I tried this experiment was mostly to test the argument that we didn't actually need 16 channels. But while the RGB conversion algorithm and PCA are fundamentally different, they ultimately arrive in the same data shape: they reduce the number of channels from 16 to 3.

Therefore, after PCA, I once again applied SLIC before applying HDBSCAN, resulting in the following image:

![PCA cube](/assets/img/posts/week10/pca_hdbscan_epsilon_1.0_min_samples_1.png)

Unexpectedly, the result of this experiment was somewhat better than the previous. While the two text components do not clearly represent either type of text, the text components now resemble letters, eventhough some of the text was still lost.

Moving to the RGB conversion, I decided to apply the clustering on it to compare the results with the LAB representation we'll use later.

By applying SLIC to the RGB image and then HDBSCAN, we get the following image:

![RGB cube](/assets/img/posts/week10/to_RGB_hdbscan_epsilon_1.0_min_samples_1.png)

Observe that the texts are now split into many different components, whilst the finer portions of it have been entirely lost. This result is arguably worse than the previous one using PCA.

By converting the colors from RGB to LAB and then applying the same algorithms as before, we get:

![LAB cube Euclidian](/assets/img/posts/week10/to_lab_hdbscan_epsilon_1.0_min_samples_1.png)

As we can see, major portions of text were still lost, but the result is still somewhat better than the RGB one. The text components are still split into many clusters, but some of the letters are readable. This suggests the clustering was conservative enough to separate text from paper. Another important observation is that the text components are consistent across all lines, which shows the clusters are not random.

Finally, by using CIEDE2000 instead of Euclidian distance in the HDBSCAN, we get:

![LAB cube ciede2000](/assets/img/posts/week10/ciede2000_to_lab_hdbscan_epsilon_1.0_min_samples_1.png)

In comparison with the last experiment, there really isn't much of a difference. The biggest one is the light gray component, which seems to behave strangely. It seems to appear between two close chunks of text. If you compare the image with the original RGB conversion, you'll see this light gray component connects patches of text that were originally continuous in the actual manuscript.

The results of these experiments show the suggested pipeline might actually work, but it still needs more improvement. To add to this, I should point out, though, that both SLIC and HDBSCAN can lead to extremely different results depending on the choice of hyperparameters. This suggests a need for hyperparameter tuning, which was not done in this post. We'll come back to this pipeline in the coming posts.
